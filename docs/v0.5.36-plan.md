# v0.5.36 实施方案 · token SBI 切换 loading + QuickPick 卡顿彻查与修复

> 目标:修两个用户报告的问题。方案先经 03_审查测试清单审查,无误再实施。

## 问题 1:token SBI 切换 tab 时数字残留(≤500ms)

### 现象
切换 CC tab 后,右下角 token 统计的**数字内容**仍显示旧 tab 的值,要等下一次 §G tick(500ms 周期)才刷新为新 tab 的数据。v0.5.35 的 `onDidChangeViewState` 只做到了** sid 即时更新**,但 SBI 的数字渲染仍由 §G tick 驱动。

### 根因(已确认)
- `onDidChangeViewState` 处理器(@101351)在 tab 激活时即时写 `__ccsdActiveSid` / `__ccsdLastActiveSid`。
- 但 `tsbi.text`(数字)只由 §G tick(@2405)每 500ms 重算 `readTok(activeSid)` 后覆盖。
- 两次 tick 之间 ≤500ms 窗口内,SBI 显示旧 tab 残留数字。

### 修复
在 `onDidChangeViewState` 处理器内,更新 sid 后**立即**把 token SBI 设为 loading 图标,并**重置 dedup sentinel**:

```js
// 紧跟在 globalThis.__ccsdLastActiveSid=t.__ccsdSid; 之后
if(globalThis.__ccsdTokSbi){globalThis.__ccsdTokSbi.text="$(loading~spin)";globalThis.__ccsdTokSbiLastText="";}
```

### 为什么必须重置 `__ccsdTokSbiLastText`
§G tick 的 4 个 `tsbi.text=` 赋值分支(正常值 / "0 tok" / catch fallback / 无 sid "—")**每个**都用 `__ccsdTokSbiLastText !== "<目标值>"` 做去重守卫(避免 steady 态每秒 ~2 次冗余 IPC 写渲染器)。若只设 loading 不清 sentinel,新 tab 真实值恰好等于旧 sentinel 时,下一 tick 会跳过写入 → loading 图标卡住。sentinel 清为 `""` 后,4 分支的 `!== "<任一常量>"` 必为真 → 下一 tick 必然覆盖。loading 最长存活 ≤500ms(一个 tick 周期)。

### R-INT-07 评估(运行时同源耦合)
- **新writer**:`onDidChangeViewState` → `tsbi.text`(§G tick 是既有 writer)。
- **交接契约**:switch 时设 loading + 清 sentinel → §G tick ≤500ms 内必然覆盖为真实值。
- **故障面**:onDidChangeViewState 已在外层 try/catch;若设 loading 抛异常,§G tick 不受影响继续正常刷新。若 §G tick 抛异常(已 try/catch),loading 可能多留 N×500ms,直到下次成功 tick。**有界、有终止符、非失控耦合**。
- 结论:合规。在注释中写明交接契约。

## 问题 2:QuickPick 配置面板初次加载卡顿

### 现象
点击右下角 token SBI 调出配置面板(`showTokQuickPick`),**初次**点击延迟很高,有"卡死"感。

### 彻查(已测量代码路径,排除以下)
| 候选瓶颈 | 实测 | 结论 |
|---|---|---|
| `readTok()` readFileSync+JSON.parse | 状态目录当前无 `<sid>.json`(ENOENT 或 <5KB 文件),<1ms | ❌ 非瓶颈 |
| §F 聚合 readdirSync+stat×N | 状态目录 9 文件,<5ms | ❌ 非瓶颈 |
| showTokQuickPick 全部同步工作 | getConfiguration + 6×cfg.get + readTok + 15 items 构造,<15ms | ❌ 非瓶颈 |
| §G tick computeLiveDelta 争用 | 仅当活跃会话 jsonl 巨大(如 2GB observer)时读 512KB 尾,20-60ms;点击恰好落在 tick 期间才排队 | ⚠️ 次要因素 |

### 真实瓶颈(推断 + 待插桩确认)
1. **`vs.window.showQuickPick` 冷启动**(主因):VSCode QuickPick UI widget 首次创建 + codicon 字体首次加载,200-500ms。这是 VSCode 内部成本,扩展代码无法消除。
2. **状态栏点击无视觉反馈**:StatusBarItem 无 pressed 态,用户点击后到 picker 出现之间无任何反馈 → "卡死感"被放大。
3. **EH 线程争用**(次要):若点击恰好落在 §G tick computeLiveDelta 期间,命令排队 20-60ms。

### 修复(防御性,无论瓶颈在哪都生效)
1. **`vs.window.withProgress`(Notification spinner)**:点击即时显示 spinner,给视觉反馈。
2. **`setImmediate` 推迟重活**:点击命令处理器立即返回,EH 不阻塞,VSCode 保持响应。
3. **CCSD_DEBUG 插桩**:给 showTokQuickPick 各阶段(getConfiguration / readTok / item-build / showQuickPick 出现)加 timing log,确认瓶颈 + 供未来诊断。

### 代码结构
